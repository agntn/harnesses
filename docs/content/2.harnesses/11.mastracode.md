::harness-facts{id="mastracode"}
::

Mastra Code stores everything it remembers in one LibSQL database under `~/.local/share/mastracode/` on Linux, threads and messages alongside its observational memory. Hooks are a JSON file rather than a directory, at project and user scope, and MCP servers sit in `.mastracode/mcp.json` and its global twin.

It reads Claude's files as its own: `CLAUDE.md`, `.claude/CLAUDE.md`, `~/.claude/CLAUDE.md` and both skills directories, beside `AGENTS.md` and `.mastracode/`. No non-interactive mode is recorded, so `invoke` rejects before spawning and the CLI's `run` refuses it with the same message. MCP servers come from four local files, lowest first: `mcpServers` in the project's `.claude/settings.local.json`, `~/.mastracode/mcp.json`, the project's `.mcp.json` and `.mastracode/mcp.json`, later names winning, with `~/.claude.json` and Codex's `config.toml` joining on opt-in. The registry maps the three that are MCP files, so `listMcpServers` reads them and `syncMcpServers` rewrites the user one. Project writes go to `.mastracode/mcp.json`, and `.mcp.json` is listed as Claude's to edit. The settings file is Claude's too and stays out. All of them are the plain `{ command, args, env }` and `{ url, headers }` family, and the `type` field means nothing to Mastra Code: an entry is stdio when it has `command`, HTTP when it has `url`, and SSE gets settled at connect time. That's why the registry gives it its own `mastracode` dialect. A stale `type` next to a `command` doesn't turn the listing into SSE, the writer leaves `type` out, and an `enabled` flag on the master list is dropped rather than rewritten on every sync, because Mastra Code has no such switch.
