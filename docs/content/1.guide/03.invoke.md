## invoke

```ts
import { getHarness } from "@agntn/harnesses";

const codex = getHarness("codex");

const result = await codex.invoke("Review this patch for races", {
  readOnly: true,
  timeoutMs: 60_000,
});

result.command; // "codex"
result.args; // ["exec", "--skip-git-repo-check", "--sandbox", "read-only", "Review this patch for races"]
result.stdout; // whatever Codex printed
result.exitCode; // number, or null when stopped by a timeout or a signal
```

`invoke` expands the harness's argument template, spawns the binary with `stdio` piped, and resolves with the captured output. An exit code other than zero is a result, not an exception. It does throw when the requested mode has no template, before anything is spawned. It also throws when the spawn fails. Node's `spawn claude ENOENT` reads the same for a missing binary and a missing working directory, so the message names which one it is. `code` stays Node's. `buildInvocation(prompt, options)` gives you the command without running it, `invocationError(options)` the reason it would be rejected, or `null`.

There's one more refusal. `invoke` sets `AGNTN_HARNESSES_PARENT` to the harness id on the process it starts, and Grok, for one, passes its environment to its MCP servers. So when that harness calls `harnesses_run` back, the nested `invoke` throws before spawning anything. That's on purpose. Grok in read-only mode calling Grok through the MCP server got a child with no network in its sandbox, which retried quietly until the deadline, and the caller saw nothing but silence.

## Modes

`tools` defaults to `false`. That gives an advisor: the harness with its tools removed by a native CLI flag, so the model can only answer. It is not an agent told to behave by prompt wording.

| Option set | Mode | Needs |
| --- | --- | --- |
| `{}` | advisor | `noToolsArgs` |
| `{ structured: true }` | advisor, JSON output | `noToolsJsonArgs` |
| `{ readOnly: true }` | full agent in a native read-only sandbox | `readOnlyArgs` |
| `{ readOnly: true, structured: true }` | same, JSON output | `readOnlyJsonArgs` |
| `{ tools: true }` | full agent | `args` |
| `{ tools: true, structured: true }` | full agent, JSON output | `jsonArgs` |

`readOnly` implies `tools` when you leave `tools` out. An explicit `tools: false` beside it is rejected, since a read-only agent still has tools. A harness that lacks the template for the requested mode rejects the call and says which retry would work:

```
Harness gemini has no read-only full agent invocation
Harness codex has no advisor without tools invocation; retry with tools: true to start its full agent
```

Codex has no advisor because `codex exec` cannot switch its tools off. OMP has `--no-tools`, but it only disables the bundled tools, so it doesn't count either. Claude's `--tools ""` with `--strict-mcp-config` does. `harness.invocationModes` tells you the six booleans up front, and every harness page lists its templates. Nothing falls back to a wider mode, ever.

Taking the tools away doesn't tell the model they're gone, though. Ask a toolless Claude to hash a string in node and it writes the `<invoke name="Bash">` block itself, as plain text. In longer runs it then reports what that run returned. Nothing ran. So Claude's advisor templates append a system prompt saying there are no tools here. Any advisor answer that still holds an `<invoke>` or `<function_calls>` tag comes back with `toolCallsAsText: true`. `harnesses_run` adds a `warning` for the model, `harnesses run` prints it on stderr. The exit code stays put, because the rest of the answer can still be fine.

Read-only can take the network too. Grok's sandbox cuts it on Linux for everything Grok starts, MCP servers included, while its own search keeps working. So the run finishes and looks fine. And the web tools it leaned on? Dead, every one. `harness.readOnlyNetwork()` says so before the run: `false` for Grok on Linux, `true` on macOS. `null` means nobody checked, not that the network is there. A run that needs the web wants `tools: true` without `readOnly`.

Pi and Claude Code do read-only with a tool list instead. Pi keeps `read`, `grep`, `find` and `ls`. Claude Code keeps `Read`, `Glob` and `Grep`. Every extension and MCP tool stays outside, so on Pi it's a library card for four shelves.

Vibe gets there from the other side. Its read-only run switches off every tool but `read_file`, and what survives is a sandbox for `run_typescript` that can't touch a file. Bash, edits, subagents, skills, MCP: all denied.

Losing a whole run to "tool not available" is a silly way to find that out. `harness.readOnlyTools()` names the list before the run. Need a tool that isn't on it? Then you want `tools: true` without `readOnly`. Codex and Grok answer `null`, since a sandbox decides there, not a list.

## Models

```ts
const pi = getHarness("pi");
const { models } = await pi.listModels({ search: "gpt-5.4" });
models[0]; // { provider: "openai-codex", id: "gpt-5.4", contextWindow, maxOutputTokens, thinking, images }

await pi.invoke("Review this patch", { model: "openai-codex/gpt-5.4", readOnly: true });
```

`model` appends the harness's `modelArgs`. A harness without them rejects the option. `listModels` runs the native listing command and normalizes its output. Pi, Prime Agent, OMP, Grok, Antigravity, Codex and Kilo have one today.

The outputs differ, of course:

- Pi, Prime Agent and OMP list only providers with configured authentication.
- OMP prints JSON, so there's no table to parse, and it lists chat models only.
- Grok prints bare ids with the default marked, so its models carry `default` and none of the size or feature fields.
- Antigravity prints an id and a display name with no default, so its models carry the id and the `google` provider only.
- Codex dumps its whole catalog as JSON. Its models carry a display name in `name`.
- Kilo prints one `provider/model` per line, and ids keep their own slashes (`kilo/~anthropic/claude-opus-latest`), so the row splits at the first one.

`search` goes to the CLI when it has a filter of its own. Grok, Antigravity, Codex and Kilo don't, since Kilo's argument picks a provider, not a model, so there the ids are matched locally, ignoring case.

A harness without `modelListing` rejects the call too. But a bare refusal is a dead end, so Claude, Gemini, OpenCode, Vibe and Hermes add their `invocation.modelHint` to it. Claude's says you can just run with `model: "opus"` instead of sending `harnesses_models` on another treasure hunt.

## Reasoning effort

Ever asked for a yes or no and watched the harness think for seven minutes?

```ts
await getHarness("grok").invoke("Is this regex fine?", { readOnly: true, effort: "low" });
```

`effort` appends the harness's `effortArgs` for that one run. Your config stays untouched. Claude, Codex, Grok, Kilo, Pi, OMP, Vibe and Hermes take it today.

The word goes through as is, in the harness's own vocabulary. So `xhigh` means something to Grok and Claude, `minimal` to Pi. A harness without `effortArgs` rejects the option, same as `model`. Anything that isn't one lowercase word is rejected too. An effort can't smuggle in a second flag.

What happens to a word the CLI doesn't know is the CLI's call. Grok and OMP refuse to start. Claude and Pi print a warning and think as hard as their config says. Vibe warns too, then sends no thinking level at all. Codex takes it and prints it in its header.

## Without extensions

Ever lost a whole run to an extension you didn't even ask for?

```ts
await getHarness("pi").invoke("Review this patch", { extensions: false }); // no global extensions, this run only
```

Pi loads its global extensions on every run, the advisor without tools included. One that throws on load stops Pi before your prompt reaches the model. `extensions: false` appends `--no-extensions`, and the prompt gets through.

A failed Pi run that printed Pi's own hint comes back with `extensionLoadFailed: true`. That's your cue to retry without them. OMP prints its load error and keeps going, so there the option only buys a quieter start.

Pi and OMP take it, and so does Kilo, where it becomes `--pure`. Every other harness rejects it before spawning. Extensions still load by default, because they can register model providers. Skip them and your model might skip town too.

## Sessions

```ts
import { randomUUID } from "node:crypto";

const claude = getHarness("claude");
const id = randomUUID();

await claude.invoke("Review this patch", { sessionId: id, readOnly: true });
await claude.invoke("And the tests?", { resume: id, readOnly: true });

await getHarness("codex").invoke("Now the error paths", { readOnly: true, resume: threadId });
```

Want the second run to pick up where the first one stopped, without pasting the transcript again? `resume` carries the conversation into the next run. Claude, Codex and OMP take it. Only Claude takes `sessionId`, which names a new session.

Where's the id? Claude prints it as `session_id`. Codex puts `thread_id` on its first JSON line, OMP puts `id` on its first. With Claude you pick the UUID up front and skip the parsing. An id that already exists fails. Names and prefixes don't get a vote: it's a full UUID or nothing.

`resume` and `sessionId` together are rejected. So is either one on any other harness, before anything spawns. Pi can open a session too, but from another directory it stops and asks whether to fork. It sits this one out.

The mode is still chosen per run, and resuming never widens it. A read-only Codex resume stays in its read-only sandbox. That's one permission surprise fewer.

## Timeouts and cancellation

`timeoutMs` and `signal` work the same on `invoke` and `listModels`. Unset or `0` means no deadline. An already aborted signal skips the spawn. Otherwise the first of cancellation or deadline starts cleanup:

- Linux and macOS: the child runs in its own process group; `SIGTERM` to the group, then `SIGKILL` 500 ms later, even if the root already exited.
- Windows: `taskkill /T /F` at once, with a 2 s budget for that command.

A stopped result keeps the output captured so far and has `exitCode: null`. `aborted` is true when your signal won, `timedOut` when the deadline did; the first reason wins and later aborts do nothing. Cleanup failures reject the promise.

`idleMs` on a stopped result says how long both streams had been silent before the stop. A few milliseconds means the model was still writing; the whole deadline means it never printed anything. Plain `claude -p` holds its answer until the end, so a plain Claude run streams events with `--output-format stream-json` and folds them back: a finished run returns the same text as before, a stopped one the text written so far. Structured runs keep the single final JSON.

```ts
const controller = new AbortController();
const pending = pi.invoke("Review this change", { tools: true, readOnly: true, signal: controller.signal });
controller.abort();
(await pending).aborted; // true
```

This is command cleanup, not a sandbox. A descendant that leaves the process group, or outlives an already exited root on Windows, is out of reach. Output pipes inherited by such a descendant do not extend the wait.

## In the CLI

```bash
harnesses run claude "review this design"                 # advisor
harnesses run pi --model openai-codex/gpt-5.4 "review"   # advisor, chosen model
harnesses run codex --read-only "review this"            # native read-only sandbox
harnesses run grok --read-only --effort low "quick one"  # think less, this run only
harnesses run claude --tools --structured "fix lint"     # full agent, structured output
harnesses models pi gpt-5.4 --json
```

`--timeout` is in seconds. A timed out run exits 124, otherwise the harness's own exit code passes through.
