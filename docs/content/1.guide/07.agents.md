## Eleven tools, four surfaces

MCP server, Pi extension, OMP extension and AI SDK map serve the same tools. Same descriptions, same arguments, same answers. Ask from Pi or from Claude Code, the tool tells you the same thing.

| Tool | Kind | Does |
| --- | --- | --- |
| `harnesses_detect` | read | Installed harnesses, their versions and how each one runs |
| `harnesses_info` | read | Full metadata for one id, or a batch of up to 20 ids |
| `harnesses_models` | exec | Models a harness can use now, optionally filtered |
| `harnesses_run` | exec | One prompt through another harness |
| `harnesses_mcp_list` | read | MCP servers in every config, normalized, or one by name |
| `harnesses_mcp_add` | write | Add or replace one MCP server |
| `harnesses_mcp_remove` | write | Remove one MCP server |
| `harnesses_mcp_sync` | write | Reset user scope configs to `~/.config/agntn/mcp.jsonc`, or check |
| `harnesses_agents_sync` | write | Link global instructions files to the master bundle, or check |
| `harnesses_prompts_sync` | write | Sync canonical Markdown prompts into harness destinations, or check |
| `harnesses_skills_sync` | write | Link harness skills directories to the XDG data skills folder, or check |

`harnesses_info` with a list keeps the input order and returns an error entry beside the successful ones for an unknown id, so one typo doesn't fail the batch.

Its text shows every path once, under `resolved`, expanded for the machine the tool runs on and filtered to its platform. The `~` templates with their platform tags are what `harnesses info` prints. An agent doesn't need both.

## MCP

```bash
harnesses mcp
claude mcp add harnesses --scope user -- npx -y @agntn/harnesses mcp
```

Or in a client's config, or on the master list that `mcp-servers sync` distributes:

```json
{
  "mcpServers": {
    "harnesses": { "command": "npx", "args": ["-y", "@agntn/harnesses", "mcp"] }
  }
}
```

The server speaks MCP over stdio and validates every call against the published JSON Schema. Read tools are annotated read-only and idempotent; `harnesses_run` is marked destructive and open world, because it is.

## Running another harness from an agent

`harnesses_run` takes `id`, `prompt`, and `tools` as a required boolean. The model has to choose. `tools: false` is the advisor without tools, `tools: true` the full agent, `readOnly: true` beside it demands a native read-only sandbox.

A mode the target harness cannot provide comes back as a tool error with the retry that would work. It never widens access on its own. `timeoutSeconds` defaults to 600.

Not sure which modes a harness has? `harnesses_detect` tells you before the first call. Each row carries `advisor`, `readOnly` and `agent`. Codex says no to `advisor` right there. No refused run, no retry, no wasted turn.

`effort` is optional and lasts one run. `harnesses_info` says which harnesses take it, in `effortSelection`. Handy when a global config says `xhigh` and all you wanted was a yes or no. Elsewhere it comes back as a tool error, never as a run that quietly ignored it.

`extensions: false` starts Pi or OMP without global extensions and Kilo without external plugins, and `extensionsOptional` in `harnesses_info` says where that works. A Pi run that died on a broken extension carries `"retry":{"extensions":false}` in its status line. The fix is one field away, not a trip to the shell.

`resume` and `sessionId` work here too, and the status line echoes them. `harnesses_info` says where, in `sessionResume` and `sessionIdSelection`. The conversation carries over. Access doesn't: each run picks its own.

Cancellation follows the host's request signal, the one MCP, Pi, OMP and the AI SDK hand to a tool when the user interrupts. It is not a JSON argument, because a model would forget to pass it.

The answer comes back as plain text. First a status line in compact JSON: the id, the invocation, exit code and timeout state.

Then `stdout:` and the output on the lines below, capped at 8000 characters per stream, terminal control sequences stripped. A failed run adds `stderr:` the same way. A run that printed nothing on stdout shows its stderr instead.

The output isn't quoted into a JSON string. A markdown answer with code blocks reads as markdown, not as a wall of `\n` escapes.

## Pi and OMP

```bash
pi install npm:@agntn/harnesses
```

Both extensions are declared in `package.json`. Results render as a collapsed preview in the terminal, with the full text once you expand the row. `harnesses_run` output from a long review is where that matters.

::note
A second harness's answer is a hypothesis. When Claude asks Codex to review a patch through `harnesses_run`, what comes back is text to check against the code, not a verdict to paste. The tool returns it as text on purpose.
::

## AI SDK

You can use the same eleven tools in your AI SDK app.

```bash
pnpm add @agntn/harnesses ai @ai-sdk/anthropic
```

```ts
import { anthropic } from "@ai-sdk/anthropic";
import { harnessesAiTools } from "@agntn/harnesses/ai";
import { generateText, isStepCount } from "ai";

const { text } = await generateText({
  model: anthropic("claude-sonnet-5-5"),
  tools: harnessesAiTools,
  stopWhen: isStepCount(5),
  prompt: "Which coding agents are installed here?",
});
```

`harnesses_detect`, `harnesses_info` and `harnesses_mcp_list` run without approval. The other eight request it. `harnesses_run` and `harnesses_models` spawn a CLI. `harnesses_mcp_add` and `harnesses_mcp_remove` edit MCP configs. The four syncs rewrite configs and links on disk: `harnesses_mcp_sync`, `harnesses_agents_sync`, `harnesses_prompts_sync` and `harnesses_skills_sync`. Asking first is right: a run can spend another account's tokens. Your model reads the same text the MCP server returns.

Want one model to ask another for an opinion? Approve `harnesses_run` in your call:

```ts
await generateText({
  model: anthropic("claude-sonnet-5-5"),
  tools: harnessesAiTools,
  toolApproval: { harnesses_run: "approved" },
  prompt: "Ask Codex what it thinks of this diff.",
});
```
